# AI 交互 Prompt 链：三次核心迭代的完整记录

**项目**：《大肥鱼历险记 · DeepSeek 认知冒险》
**用途**：比赛材料第 3、4 项——核心功能迭代中与 AI 交互的完整 Prompt 链，以及可直接复用的有效 Prompt。

> 说明：以下 Prompt 与 AI 建议按真实迭代过程整理，保留了当时的约束、拒绝理由、Bug 现象与验证命令；代码、测试数量、截图与模拟数据均与仓库当前状态一致。AI 的回复为摘要式还原，不是逐字聊天记录。

---

## 0. 我使用的 Prompt 链结构

每一次核心迭代，我都按同一个五段式推进，而不是「一句话让 AI 写完」：

```text
① 目标卡：要做什么 + 为什么 + 验收命令
② 约束卡：不能做什么 + 必须遵守的架构/文件边界
③ 复述卡：让 AI 先复述约束、列出改动计划（不写代码）
④ 实施卡：只做最小改动 + 自测 + 输出证据
⑤ 回归卡：Bug 复现 → 根因 → 最小修复 → 全量回归
```

这套结构解决三个问题：

| 问题 | 典型表现 | 对应卡 |
|---|---|---|
| 范围漂移 | 让它修移动，它顺手重写战斗、加新依赖 | ① 目标卡 + ② 约束卡 |
| 架构漂移 | 引入框架、ES Module、后端、数据库 | ② 约束卡 + ③ 复述卡 |
| 验收漂移 | 说「已完成」，但没跑测试、没截图、旧功能坏了 | ④ 实施卡 + ⑤ 回归卡 |

## 1. 案例一：40 关体力追击重构（含 3 个用户可见回归）

### 1.1 背景

最初版本是「行动点 + 手动结束回合 + 每关刷怪」的短局制。比赛版本要求改成：

- 40 关固定战役，Boss 在 10 / 20 / 30 / 40；
- 每次只能移动一格，移动 -1 体力，攻击 -1 体力，技能 0；
- 怪物在玩家**每次行动后**沿最短路靠近，每 2 次反应攻击一次；
- 怪物只在回合开始刷新；
- 击败全部怪物自动结算，不再有「结束回合」按钮；
- 仍然是零依赖、双击即玩、无构建。

### 1.2 我的 Prompt（第一次）

```text
你是这个项目的游戏逻辑工程师。请把现有的「行动点 + 手动结束回合」改造成「体力 + 自动回合」。

【目标】
1. 战役固定 40 关，Boss 关为 10/20/30/40。
2. 玩家每次只能移动 1 格；移动消耗 1 体力，普通攻击消耗 1 体力，主动技能不消耗体力。
3. 每次玩家行动后，所有怪物按 BFS 最短路向玩家靠近；每 2 次怪物反应攻击 1 次。
4. 怪物只在每回合开始时刷新；回合开始体力回满、技能冷却重置。
5. 当前回合怪物全部死亡后自动进入结算，删除「结束回合」按钮。
6. 保持零依赖、无构建、index.html 双击可玩。

【不能做】
- 不引入任何 npm 依赖、框架、构建工具、ES Module。
- 不修改 js/core 之外的业务规则；不把 DOM 操作写进 core。
- 不删除现有 API 设置、结局图鉴、Boss 对话、结局 CG 功能。

【验收】
- npm test 全绿。
- 正常从标题页开始：第 1 关有怪物、有可移动高亮；移动一次体力 -1；清空怪物自动进结算。
- npm run screens 的 E2E 无运行时错误。

先不要写代码。请先复述你理解的约束，列出你打算修改的文件和每个文件的职责，并指出你认为有风险的地方。等我确认后再动手。
```

### 1.3 AI 的第一次建议（摘要）

AI 给出的方案大意是：

1. 保留行动点，把「结束回合」改成「体力耗尽自动结束」；
2. 新增 `ActionSystem`，用 A* 替换 BFS；
3. 把 `main.js` 拆成多个 ES Module；
4. 每击杀一只怪物就补刷一只，保持节奏；
5. 引入 `pathfinding` 库简化寻路。

### 1.4 我的拒绝与二次约束

我没有接受，而是逐条指出它违反的约束：

```text
你的方案有 5 处违反约束，请先不要写代码，逐条回应：

1. 我要求删除「结束回合」，不是改名；请给出没有手动结束回合的状态机。
2. 不允许新增依赖或 ES Module；A* 也不必要，9×9 网格 BFS 足够，请说明 BFS 的复杂度。
3. 怪物只在回合开始刷新；「击杀后补刷」会让回合无法结束，请删除。
4. 拆分模块可以，但必须保持现有 script 顺序与 UMD 包装，不能改成 import/export。
5. 请列出「正常开始游戏」这条路径上，从点击职业卡到第一只怪物出现的完整调用链，确认 startRound 只被调用一次。

输出格式：
- 违反项 → 修正方案（一行一条）
- 改动文件清单（只允许 js/core/progression.js、js/core/monsters.js、js/core/state.js、js/ui/hud.js、js/ui/input.js、js/main.js）
- 你认为最容易回归的 3 个旧功能
```

AI 第二次建议收敛为：

- 用 `state.player.stamina` 替代 AP，`Stats.compute` 增加 `stamina`；
- `startRound` 负责刷新、回满、重置冷却；
- `movePlayer` 只允许曼哈顿距离 1，扣体力，然后 `Monsters.reactAll`；
- `afterPlayerAction` 在 `monsters.length === 0` 时进入 `reward`；
- 保留 UMD 与 script 顺序。

这次方向正确，我让它按文件逐个改，每改完一个文件就跑一次测试。

### 1.5 实施后的用户 Bug 报告

重构完成后，实际点击出现 3 个问题：

```text
现在的 bug 有：
1. API 设置选项点击没有反应；
2. 结局图鉴点击没有反应；
3. 开始冒险后，无法移动，且不刷怪。
```

### 1.6 我的 Bug 诊断 Prompt（关键：禁止先改）

```text
不要直接改代码。先做根因诊断。

现象：
- 标题页「API 设置」「结局图鉴」点击无反应；
- 正常开始冒险后，棋盘没有怪物，也没有可移动高亮；
- 但通过 ?dev=1&stage=3 直接开局时，有时能看到怪物。

已知：
- 重构只应改体力/回合/怪物反应；
- 标题页按钮 id 没有变；
- main.js 被重写过；
- Node 单元测试全绿，说明 core 逻辑大概率没问题。

请输出：
1. 按可能性排序的根因假设（最多 5 条），每条给出「如何用 1 条命令或 1 个 DOM 查询验证」；
2. 每条假设对应的最小修复点（文件 + 函数），先不要写完整代码；
3. 你认为单元测试为什么没抓到这些问题的原因。
```

AI 的诊断（摘要）：

| 假设 | 验证 | 结论 |
|---|---|---|
| 重写 `main.js` 时漏绑 `#btn-api` / `#btn-gallery` | 控制台查 `getEventListeners` 或点击后看 modal | 成立 |
| 正常开始路径没有调用 `P.startRound`，只有 dev 路径调了 | 在 `startRun` 打断点/日志 | 成立 |
| HUD 仍按旧 AP 字段渲染，`stamina` 为 undefined | 查 `#stamina-num` 文本 | 成立 |
| `endRound` 仍等待手动按钮 | 搜索 `btn-end-turn` | 成立 |
| 怪物生成被 `pendingQuestion` 提前拦截 | 第 1 关不应有 question | 不成立 |

根因：`main.js` 是旧控制器，新增的 `startRun`、按钮绑定、HUD 体力渲染没有接上；单元测试只测 core，不测「标题页 → 选职业 → 开局」的 UI 编排，所以全绿但游戏不可玩。

### 1.7 我的修复 Prompt

```text
根因已确认，按最小修复执行，不要重构：

1. 在 init() 中补绑 #btn-api、#btn-gallery、#btn-dev，并确保 openApiSettings / openGallery 可被调用。
2. 正常开始路径必须是：点击职业卡 → startRun(classId) → State.createRun → showScreen('game') → Hud.mount → Render.init → P.startRound(run, events, true) → handleRoundEvents。
3. HUD 的体力数字读取 state.player.stamina；删除所有 AP / 结束回合残留。
4. 加一条 E2E：从标题页点击开始 → 剧情 → 选职业 → 断言 .entity-monster >= 1 且 .tile.reachable >= 1。
5. 修完跑 npm test、npm run screens -- --e2e，把输出贴给我；如果有失败，先修失败再汇报。

只允许改 main.js、hud.js、input.js 和 tests/ 下相关文件。不要动 core 的数值。
```

### 1.8 修复结果与验证

- 标题页两个按钮恢复；
- 正常开局刷怪、移动高亮、体力扣减恢复；
- 新增 E2E 覆盖「正常开始」路径；
- `npm test` 119/119；
- `npm run screens` 25 张截图 + 6 组 E2E（7 项断言），运行时错误 0。

### 1.9 这次迭代学到的

1. **验收标准必须写在 Prompt 第一段**，否则 AI 会按「能跑」而不是「能验收」优化。
2. **让 AI 先复述约束**，比事后返工便宜得多。
3. **单元测试全绿不等于游戏可玩**；必须有一条从标题页开始的 E2E。
4. 修 Bug 时先说「不要改，先诊断」，能避免 AI 用大范围重写掩盖根因。

## 2. 案例二：AI 误解诊疗 + 12 结局系统（含不可达结局 Bug）

### 2.1 背景

原版是「每 2 关一道固定选择题」，答案只影响一个分数。比赛版本要升级为：

- 10 个 AI 使用病例，分布在第 4、8、12…40 关；
- 每个病例三步：诊断 → 检查（最多 2 项）→ 处方（选项 + 自由文字）；
- 七维认知档案：AI 理解、批判性思维、动手实践、隐私安全、提示词、科普传播、AI 依赖；
- 12 个结局 + 12 段 CG，最终对话选择 + 认知档案共同判定；
- 配 DeepSeek 时由 AI 点评处方，不配时本地评分，**不能卡关**。

### 2.2 我的 Prompt（第一次）

```text
把现有的固定选择题升级成「AI 误解诊疗」系统。

【内容】
- 10 个病例，第 4/8/12/16/20/24/28/32/36/40 关各一个。
- 每个病例：场景 + 3 个诊断选项 + 3~4 个检查选项（最多选 2）+ 3 个处方选项 + 自由补充文字。
- 七维认知档案：knowledge / critical / practice / privacy / prompt / teaching / reliance。
- 12 个结局，最终对话有 9 个选项；结局由 finalChoice + 七维共同判定。

【AI 评分】
- 配了 DeepSeek：只点评「处方/解释」，返回严格 JSON：
  {"score":0-100,"feedback":"80字以内","axes":{...0-5}}
- 没配 API 或调用失败：本地关键词 + 选项规则评分，必须能继续游戏。
- 病例结论写入认知档案，影响结局。

【约束】
- 不新增依赖；不把 API Key 写进前端代码。
- 诊断和检查由本地规则计分，AI 不重复扣分。
- 任何 API 异常都不能阻塞关卡推进。

【验收】
- 10 个病例都能完整走完三步。
- 12 个结局都有可达路径，写测试枚举。
- 断网时 12 结局仍可解锁。
- npm test 全绿。

先给出数据结构和评分分工，不要写代码。
```

### 2.3 AI 的第一次建议（摘要）

AI 建议：

1. 让 LLM 生成病例、评分三步、直接决定结局；
2. 把整段对话历史发给模型，让模型维护「认知档案」；
3. 用官方 SDK 调 API；
4. 结局判定也交给模型，前端只展示。

### 2.4 我的拒绝理由与修正

```text
这个方案不可验收，原因：
1. 结局由模型决定 → 同样的选择可能得到不同结局，无法写确定性测试。
2. 让模型评分诊断/检查 → 与本地规则重复计分，分数不可解释。
3. 引入 SDK → 违反零依赖；浏览器直连还有 CORS。
4. 整段对话历史 → token 成本高，且会把隐私内容反复上传。

改为「本地规则负责可解释部分，AI 只负责处方文字质量」：
- 诊断 35 分（本地）
- 检查 30 分（本地）
- 处方 35 分（选项 30 本地 + 文字 5 本地；配 API 时用 AI 的 score 替换这 35 分）
- axes 本地先算，AI 只补充 0-5 的增量，最后 clamp 到 0-5。

请给出：
1. Case / Answer / Judged / Record 四个数据结构；
2. AI JSON 的严格 schema 与解析失败的回退路径；
3. 12 个结局的判定表（finalChoice × axes 阈值），标出哪些组合目前不可达。
```

### 2.5 实施后发现的 Bug

**Bug A：部分结局理论上不可达。**

测试枚举发现：`promptMaster` 和 `privacyGuard` 只能靠 axes 阈值触发，而最终对话没有对应选项；当玩家明确想走「提示词」或「隐私」路线时，会被别的分支截走。测试 helper 又直接构造 axes，掩盖了真实入口缺失。

**Bug B：AI 返回 Markdown 代码围栏时解析失败。**

模型返回：

```text
```json
{"score": 82, ...}
```
```

`JSON.parse` 直接失败，反馈框为空，玩家以为游戏卡住。

### 2.6 我的诊断 Prompt

```text
先不要改。请做两件事：

【任务 1：可达性证明】
写一个测试矩阵，枚举 finalChoice 的 9 个取值 × 七维的边界组合（0 / 阈值-1 / 阈值 / 100），
对每个组合调用 Endings.resolveEnding，统计 12 个结局各自被哪些组合命中。
输出：
- 每个结局的最短触发路径（finalChoice + 关键 axes 阈值）；
- 完全不可达的结局列表；
- 只能靠「测试直接构造 axes」到达、真实玩法到不了的结局列表。

【任务 2：解析鲁棒性】
列出 AI 可能返回的 5 种非纯 JSON 形式（代码围栏、前后解释、单引号、截断、多 JSON），
给出一个不引入依赖的解析策略，并说明解析失败时 UI 应该显示什么。

仍然不要写代码。
```

AI 的结论：

- `promptMaster` / `privacyGuard` 缺少显式 finalChoice 入口，真实玩法只能靠 axes 碰运气；
- `teach` 也没有独立入口，和 `popularizer` 的映射不完整；
- 解析应先剥离 ```json 围栏，再取第一个 `{` 到最后一个 `}`，失败则回退本地评分并 toast；
- `normalizeJudged` 必须保留 `source`，否则 `applyAnswer` 不认 AI 分。

### 2.7 我的修复 Prompt

```text
按诊断结果做最小修复：

1. 最终对话补 3 个显式选项：prompt（整理提示词手册）、privacy（写隐私守则）、teach（回学校科普）。
2. resolveEnding 增加显式分支：
   - prompt → promptMaster
   - privacy → privacyGuard
   - teach → popularizer
3. 保留 axes 兜底，但显式选择优先。
4. AI 解析加 parseJsonLoose：去 ```json 围栏 → 截取首尾大括号 → JSON.parse；失败返回 null。
5. AI.judge 失败或解析失败时，返回 {ok:false,error}，main.js 必须 toast 并回退 Questions.localJudge。
6. 新增测试：
   - 9 个 finalChoice 各自至少命中一个结局；
   - 12 个结局全部可达；
   - 代码围栏 JSON 能解析；
   - 解析失败会回退本地分。
7. 跑 npm test，把新增测试名和结果贴出来。

不要改病例文案与数值。
```

### 2.8 验证结果

- 12 个结局全部可达；
- 9 个最终选项均有确定映射；
- 代码围栏 / 前后解释 / 截断 JSON 均有回退；
- API 失败不会阻塞关卡；
- `npm test` 119/119，含新增可达性测试；
- E2E 走通「终局对话 → 结局 CG → 结算 → 图鉴解锁」。

### 2.9 这次迭代学到的

1. **「有 12 个结局」不等于「12 个结局可达」**；要让 AI 写可达性矩阵，而不是只写分支。
2. **LLM 只做它擅长的部分**：自然语言点评；判定、计分、状态推进留在本地。
3. **严格 JSON 也要容错**：模型加代码围栏是常态。
4. **测试 helper 不能绕过真实入口**，否则会制造「测试通过但玩法不可达」的假象。

## 3. 案例三：37 帧精灵动画与抠图管线（含白边、比例、锚点 Bug）

### 3.1 背景

两个职业从 emoji 占位升级为原创立绘 + 攻击动画：

- 输入：一张立绘 PNG + 一段 3.04 秒、24fps 的 mp4；
- 输出：37 帧、300×400 画布、8 列 × 5 行图集；
- 游戏内 2.5 倍速播放（约 1.23 秒）；
- 待机与攻击必须共用脚底锚点（格子高度 82%），切换不跳大小、不跳位置；
- 不改角色颜色、不重绘角色。

### 3.2 我的 Prompt（第一次）

```text
写一个 Python 构建脚本，把立绘 + 攻击视频转成游戏精灵图集。

【输入】
- 立绘：assets/<class>/portrait.png
- 视频：3.04s / 24fps，角色背景为纯色或渐变
【输出】
- 37 帧，300×400 画布，8 列 × 5 行，WebP 图集
- 同时输出 JSON manifest：frames / fps / impactFrame / footFraction / characterHeightPx

【硬性要求】
1. 不改变角色本身的颜色与比例，只做背景去除与画布对齐。
2. 待机图与攻击图必须共用脚底锚点：脚底落在格子高度的 82%。
3. 角色本体在棋盘上约 1.6 格高；两个职业切换不能一大一小。
4. 游戏内 2.5 倍速播放；命中帧必须落在动画约 0.6-0.7 秒处。
5. 透明区域不能挡住棋盘点击。

【验收】
- 生成 37 帧，帧尺寸一致；
- 首帧与待机图叠加，脚底与身高对齐；
- 逐帧检查无白边/绿边；
- 真实 Chrome 截图 8 张，无运行时错误。

先说明你打算怎么抠图、怎么定锚点、怎么验证，不要直接写完整脚本。
```

### 3.3 AI 的第一次建议（摘要）

1. 用固定绿幕键 `#00ff00` 做 chroma key；
2. 每帧按非透明像素的包围盒裁剪，再缩放到 300×400；
3. 按视频原生 24fps 播放；
4. 把精灵居中到格子；
5. 用 CSS `mix-blend-mode` 去白边。

### 3.4 我的拒绝与约束

```text
方案有 4 个问题：
1. 魔法师的视频背景是「白 → 绿」渐变，固定绿幕会留下大片白边；请改成逐帧估计背景色。
2. 按包围盒裁剪会让每一帧的角色大小跳动；必须固定 300×400 画布，用脚底锚点对齐。
3. 原生 24fps 播 3 秒太慢；游戏内要 2.5 倍速，命中帧对齐到 0.6-0.7 秒。
4. mix-blend-mode 会受棋盘背景影响，不能作为去边方案；请在构建期解决。

请给出可测量的验证指标：
- 每帧透明像素占比；
- 首帧/命中帧/末帧的脚底 y 坐标与角色高度；
- 待机图与攻击首帧的脚底偏差（像素）；
- 边缘像素的 RGB 分布（判断是否残留白边/绿边）。
```

### 3.5 实施后发现的 Bug

| Bug | 现象 | 根因 |
|---|---|---|
| 白边 | 魔法师头发边缘有 1–2px 白圈 | 视频背景由白渐变到绿，固定键色把白边当半透明 |
| 绿边 | 战士三叉戟边缘泛绿 | 直接键绿后没有反预乘/去色边 |
| 比例跳变 | 待机 1.6 格，攻击瞬间变成 2.9 格 | 每帧按包围盒缩放，没有固定画布 |
| 锚点漂移 | 攻击时角色脚底上下跳 | 用包围盒底边当脚底，而不是固定 `footFraction` |
| 挡点击 | 攻击图透明区域盖住相邻格子，点不动 | 精灵元素没有 `pointer-events:none` |
| 命中帧偏晚 | 技能白环炸开时，伤害数字还没出 | `impactFrame` 按 24fps 估算，没按 2.5 倍速换算 |

### 3.6 我的诊断 Prompt

```text
不要凭感觉调参。先用数据定位：

我提供三帧：首帧、命中帧、末帧。
请写一个诊断脚本，输出：
1. 每帧四角与边缘中位色（判断背景色漂移）；
2. 每帧非透明像素的 bbox（x/y/w/h）与脚底 y；
3. 待机图与攻击首帧的脚底偏差、角色高度偏差；
4. 边缘 2px 内「接近白色」和「接近绿色」的像素比例。

然后回答：
- 白边是键色残留还是反预乘错误？
- 比例跳变是画布问题还是缩放问题？
- 命中帧应该用第几帧，按什么公式算？
- 哪些问题应该在构建期修，哪些在渲染期修？

先给诊断结论，不要改代码。
```

AI 的诊断结论（摘要）：

- 白边来自「固定键色 + 未反预乘」；魔法师必须逐帧取边缘中位色，再做泛洪填充；
- 比例跳变来自「按 bbox 缩放」；应固定 300×400 画布，只做统一比例映射；
- 脚底应使用构建期测得的 `footFraction`，而不是每帧 bbox；
- 命中帧按 `impactFrame / (fps * playbackSpeed)` 换算，战士 21 帧 ≈ 0.7s，法师 19 帧 ≈ 0.63s；
- `pointer-events:none` 属于渲染期修复。

### 3.7 我的修复 Prompt

```text
按诊断做三类修复，不要重绘角色：

【构建期】
1. 逐帧取边缘中位色作为背景色，灌水填充；再叠加全局绿键与边缘 alpha 收边。
2. 反预乘去除白边；对边缘 1px 做去色，不允许改动角色内部像素。
3. 固定 300×400 画布；用统一比例把角色映射进去；脚底固定在 footFraction。
4. 输出 manifest：frames/fps/impactFrame/footFraction/characterHeightPx。
5. 重新生成战士与法师两套图集。

【渲染期】
6. 精灵容器 pointer-events:none；只有格子可点击。
7. 播放速度 2.5；按 impactFrame 触发命中特效。
8. 待机与攻击共用同一个脚底锚点，切换时不能改变容器尺寸。

【验收】
9. 生成 37 帧，帧尺寸全部 300×400。
10. 写测试断言两套 manifest 与 config.js 一致、原图哈希未变。
11. 跑 verify_warrior / verify_mage，各 8 张真实截图，逐帧推进后能回待机。
12. 报告：脚底偏差、角色高度、白边/绿边像素比例。

先改构建脚本，再改渲染；每步跑完把数据贴出来。
```

### 3.8 验证结果

- 战士：37 帧，角色高 214px，脚底 351.1，`footFraction 0.87771`，命中帧 21；
- 法师：37 帧，角色高 164.1px，脚底 293.8，`footFraction 0.7344`，命中帧 19；
- 两套图集均为 300×400，游戏内 2.5 倍速约 1.23 秒；
- 棋盘上两人角色本体都约 1.6 格高，切换职业不跳大小；
- 透明区域不挡点击；
- 专项验收各 8 张截图，无运行时错误；
- 原图 SHA-256 未变（战士 `49eb6570…`，法师 `5cfcfcea…`）。

### 3.9 这次迭代学到的

1. 把「看起来不对」翻译成**可测量指标**（脚底 y、bbox、边缘像素比例），AI 才能稳定修。
2. 构建期问题与渲染期问题要分开，混在一起调参只会互相掩盖。
3. 固定画布 + 固定锚点，比每帧自适应更可靠。
4. 视觉验收也要有自动化：截图 + 帧推进 + 哈希断言。

## 4. 有效 Prompt 清单（可直接复用）

以下 6 条是我在三次迭代中反复使用、并验证有效的 Prompt。使用时把 `{{...}}` 替换成项目事实。

### 4.1 需求冻结 Prompt

```text
你要在现有项目上完成一个功能。先不要写代码。

【现状】{{一段话描述现有实现 + 相关文件}}
【目标】{{3-6 条可观察的行为}}
【非目标】{{明确不做什么，防止范围漂移}}
【硬约束】{{零依赖/不换架构/不改的文件/性能/兼容性}}
【验收】{{可执行的命令 + 可观察的页面结果}}
【输出】先复述约束，再给改动文件清单与风险点，等我确认后再写代码。
```

### 4.2 架构守门 Prompt

```text
在开始前，请检查你的方案是否违反以下架构不变量：
1. 不新增运行时依赖，不引入构建步骤。
2. core 层不出现 DOM/window/document；UI 层不直接改 state。
3. 所有 core 动作返回 {ok, reason, events}，UI 只消费事件。
4. 数值只能来自 config.js，内容只能来自 questions.js / endings.js。
5. 随机必须走 state.rng，不能新增 Math.random 到玩法逻辑。
6. 不删除或改名现有按钮 id / localStorage key / URL 参数。

逐条回答「遵守 / 违反 + 原因」。只要有 1 条违反，就重写方案，不要进入编码。
```

### 4.3 Bug 根因诊断 Prompt（禁止先改）

```text
不要直接改代码。先做根因诊断。

【现象】{{可复现步骤 + 期望/实际}}
【证据】{{控制台错误、截图、测试输出、相关文件}}
【已知边界】{{最近改过什么、哪些功能是好的}}

请输出：
1. 按可能性排序的根因假设（≤5 条），每条附一个验证命令或 DOM 查询；
2. 每条假设对应的最小修复点（文件 + 函数），先不写完整代码；
3. 为什么现有测试没抓到；
4. 修复后要补哪一条回归测试。
```

### 4.4 最小修复 Prompt

```text
根因已确认：{{一句话}}。按最小修复执行，不要重构。

只允许修改：{{文件白名单}}。
必须保持：{{接口/行为/存档键/按钮 id}}。
修复步骤：{{1-5 条}}
回归要求：{{测试命令 + E2E 路径 + 截图}}
输出：修改摘要、测试输出、仍然存在的风险。若失败，先修失败再汇报。
```

### 4.5 验收证据 Prompt

```text
不要说「已完成」。请用证据回答：
1. 运行了哪些命令？贴出最后 20 行输出。
2. 新增/修改了哪些测试？测试名是什么？
3. 真实浏览器里走了哪条路径？截图/断言是什么？
4. 哪些旧功能可能受影响？你验证了哪几个？
5. 还有哪些已知未验证项？
没有证据的条目，明确写「未验证」，不要猜。
```

### 4.6 复现文档 Prompt

```text
把当前项目写成一份「10 分钟极速复现指南」，读者是一台干净电脑上的评委。

必须包含：
1. 依赖清单（必需/可选/仅重建素材），每项写不装的后果；
2. 环境变量模板（名称/必填/默认/敏感/说明）与三种注入方式；
3. 从解压到看到标题页的最短路径；
4. 10 分钟时间盒（每段的时间 + 通过标准）；
5. 可逐项打勾的验收清单；
6. 常见故障表（现象/原因/处理）；
7. 明确写出不能保证的边界。

要求：命令可直接复制；不要写「自行配置」；不要假设读者知道你之前的目录结构。
```

## 6. 效果对照

| 指标 | 一句话 Prompt 阶段 | 使用五段式 Prompt 链后 |
|---|---|---|
| 需求理解偏差 | 经常把「删除结束回合」理解成「改名」 | 先复述约束，偏差在编码前暴露 |
| 架构漂移 | 倾向引入框架/依赖/ES Module | 架构守门 Prompt 直接拦截 |
| Bug 修复方式 | 大范围重写，旧功能回归 | 先诊断根因，再白名单最小修复 |
| 验收 | 「已完成」但无证据 | 必须贴命令输出、测试名、E2E 路径 |
| 可复现性 | 依赖作者机器状态 | 文档 + 种子 + 截图 + 模拟数据 |

> 结论：Prompt 的价值不在「让 AI 多写」，而在「让 AI 少偏离」。把目标、非目标、不变量和验收写成可执行约束，AI 才能成为稳定的工程协作者，而不是随机代码生成器。
